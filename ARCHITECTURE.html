How To Explain This in an Interview

30-Second Elevator Pitch Quick Intro

"I built an enterprise-grade payment webhook ingestion service in Django REST Framework that decouples ingestion from heavy processing. When payment gateways like Razorpay send webhooks, my service uses atomic database-level unique constraints to verify and record the transaction, pushes a job to a Celery + Redis queue, and returns HTTP 202 Accepted in under 20 milliseconds—far below the 500ms requirement. A background worker then processes the 30-second external API simulation and records the final state in an AWS RDS PostgreSQL database. Any duplicate or concurrent webhook is acknowledged gracefully without re-processing."

2-Minute Deep Dive Pitch Technical Interview
  • The Challenge: Payment webhooks cannot block on slow 30-second external calls or risk timeout penalties and duplicate retries from gateways.
  • Idempotency Guarantee: Handled at the database engine level via B-Tree unique index on transaction_id and transaction.atomic() to guard against concurrent race conditions.
  • Asynchronous Pipeline: Uses Celery with a Redis broker and a multithreaded worker pool so tasks execute concurrently without queue starvation.
  • Cloud Database & Deployment: Deployed in AWS (EC2 + Nginx reverse proxy + AWS RDS PostgreSQL instance in ap-south-1) with connection pooling (conn_max_age=600) and sub-millisecond VPC latency.

The Complete Request Lifecycle

PHASE 1 0 - 5ms

Ingestion & Validation

Webhook arrives at Nginx, forwarded to Gunicorn. DRF serializer validates types, ensures amount > 0 and currency formatting.

PHASE 2 5 - 15ms

Idempotency & Queue

Atomic get_or_create in AWS RDS. If new, enqueues Celery task to Redis broker. Returns 202 Accepted immediately.

PHASE 3 0 - 30,000ms

Async Execution

Celery worker thread picks up task, executes simulated 30s external banking delay. Meanwhile, any status query returns PROCESSING with processed_at: null.

PHASE 4 +30.01s

Atomic State Finalization

Worker issues row lock (select_for_update), updates status to PROCESSED and sets processed_at timestamp. Persisted in RDS.

04

Idempotency & Concurrency Strategy

1

Database-Enforced Index

We don't rely only on application logic for deduplication. The transaction_id column has a unique B-Tree index in PostgreSQL. Even in high-concurrency race conditions, the database engine physically rejects duplicate rows.

2

Graceful Acknowledgment

When an external gateway sends an identical webhook multiple times (common in network retries), our service intercepts the duplicate, does not re-queue a new background task, and returns 202 Accepted with an informational message.

3

Pessimistic Row Locking

In the background worker, we use select_for_update() inside a transaction block to transition the record from PROCESSING to PROCESSED. This prevents race conditions during status updates.

Key Interview Questions & Model Answers

Q1: Why did you choose Django + Celery over an async framework like FastAPI? ▼

Answer: While FastAPI excels in pure async I/O, Django REST Framework offers enterprise-grade ORM robustness, atomic database transaction controls (transaction.atomic()), mature migration management, and native integration with Celery.

Since webhook ingestion requires immediate 202 acknowledgment while offloading long operations (30s) to external processes, Celery provides a dedicated distributed task queue with process isolation, worker retry policies, and Redis broker integration, ensuring webhooks respond in under 20ms without consuming web server threads.

Q2: How do you guarantee the < 500ms latency requirement under high load? ▼

Answer: We achieve ~20ms latency through 3 key optimizations:

  1. Zero Heavy Computation in Request Loop: Webhooks do not perform external network calls synchronously; they simply push the task ID to Redis (< 2ms).
  2. Database Connection Pooling: Configured conn_max_age=600 so Gunicorn workers maintain warm TCP/SSL connections to AWS RDS PostgreSQL, avoiding repeated handshake overheads.
  3. Indexed Primary Lookups: The transaction_id is indexed with a B-Tree unique constraint for sub-millisecond lookups.
Q3: What happens if Redis or Celery workers crash? ▼

Answer: We engineered two layers of defense:

  1. Application-Level Fallback: In transactions/views.py, if Celery dispatch raises an exception (e.g. broker timeout), the service catches the error and spawns an in-process daemon thread as a fallback, guaranteeing the transaction is not lost.
  2. Systemd Process Supervision: On AWS EC2, both redis-server and transaction-worker.service are managed via systemd with Restart=always, auto-recovering within 5 seconds if killed.
Q4: How does Celery handle 30-second delays without blocking the entire queue? ▼

Answer: In standard prefork mode with 2 workers, sleeping for 30s blocks both processes. We configured the Celery worker with a thread pool (--pool=threads --concurrency=30). Because simulated external delays are I/O-bound (sleeping without CPU usage), 30+ transactions execute concurrently without queuing delays or head-of-line blocking.
